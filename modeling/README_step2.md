# Step 2: Forecasting Datasets

## What this is
`build_datasets.py` turns the raw M/M/1 time series (Step 1) into ML-ready
supervised-learning datasets for the forecasting task Azam described:
"use the recent behaviour of a queue to predict its future state, and
whether the system is moving towards congestion."

## Two feature sets (the core comparison Azam wants)
- **`history_only_rho{rho}.csv`** (Dataset A) — input is ONLY the last 10
  queue-length observations (Q_t, Q_t-1, ..., Q_t-9).
- **`rich_features_rho{rho}.csv`** (Dataset B) — the same queue-length
  history, PLUS 10-step lagged history of: number in system, arrivals per
  interval, departures per interval, recent (rolling-window) arrival rate,
  recent service rate, and a derived recent-utilisation estimate.

Comparing model accuracy on A vs. B directly answers Azam's question:
"do the additional queueing features provide a meaningful improvement over
queue-length history alone?"

## Targets (3 forecast horizons, matching "short/medium/longer")
For each row, three regression targets and three classification targets:
- `target_qlen_short` (h=5), `target_qlen_medium` (h=10), `target_qlen_long` (h=20)
  — future queue length, h observation-steps ahead
- `target_congested_short/medium/long` — binary: will the system be
  congested at that future time?

## Congestion definition used here
**Per-rho fixed threshold = 80th percentile of observed queue length for
that rho** (i.e. "top 20% of observed queue lengths" — one of the four
candidate definitions Azam listed). This was chosen over one fixed absolute
number across all rho because "congested" at rho=0.3 (queue rarely exceeds
1-2) is a completely different scale than at rho=0.95 (queue routinely
reaches 20-30+). The threshold value used for each rho is stored in the
`congestion_threshold` column of every row, and the three other candidate
definitions (absolute threshold, waiting-time threshold, utilisation-based
threshold) are easy to swap in later.

The classification target is **future** congestion (given features known
now, will the system be congested h steps ahead) — not current-state
classification — since the dissertation's framing is about forecasting,
not describing the present.

## A note on dataset size (worth logging as an "unexpected observation")
The raw simulation naturally produces far more rows at high rho (>1,000,000
at rho=0.95) than at low rho (~30,000 at rho=0.3), because high-utilisation
queues need much longer runs to reach steady state (see Step 1's README).
Left as-is, this would have produced a 300MB+ CSV at rho=0.95 alone, and
would silently make high-rho data dominate if all rho levels were combined
into one training set. To keep things practical and balanced, each rho's
processed dataset is capped at 30,000 rows via reproducible random
subsampling (fixed seed=42). This is a genuine design decision worth a line
in the methodology writeup, not just an implementation detail.

## Sanity check (worth reporting as your first baseline number)
A plain Linear Regression on Dataset A already beats the naive
"queue length stays the same" baseline at rho=0.7, medium horizon:

| Model                     | MAE   | RMSE  |
|----------------------------|-------|-------|
| Naive (persistence)        | 1.644 | 2.462 |
| Linear Regression (Dataset A) | 1.598 | 2.160 |

This is exactly the check Velarde et al. (Paper 4 in your lit review)
emphasised — always benchmark against a naive baseline before trusting any
"improvement."

## Files NOT included here
The combined `history_only_all.csv` / `rich_features_all.csv` (all 6 rho
levels concatenated) are regenerated by the script but not included in this
delivery — they're just a concatenation of the per-rho files (13MB and
50MB respectively), redundant to store separately. Regenerate them locally
by running `python build_datasets.py` if you want the single combined file
for a specific experiment (e.g. training one model across all rho levels).
